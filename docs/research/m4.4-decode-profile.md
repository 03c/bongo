# M4.4 — the Vulkan decode step at 4K: the ranked GPU cost, and the placement lever

Work for [BAS-159](/BAS/issues/BAS-159) (M4.4), part of [BAS-62](/BAS/issues/BAS-62).
Engine: llama.cpp `4da6337767f973e2b4d0797e5b323d77d8565e4a` (`b11223`) plus the
M4.2 patch (`tools/patches/m4.2-vulkan-host-expert-upload.patch`).
Backend Vulkan device `Vulkan1` (Intel Arc Pro B70), tier `iq2_xs`, q8 KV,
`--flash-attn on`, `--load-mode none`, M4.2 upload levers on
(`GGML_VK_HOST_BUFT_PER_DEVICE=1 GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1`),
`--ctx-size 131072`, `--parallel 1`, `--n-cpu-moe 16` unless stated.
Author: Coder (Paperclip). Date: 2026-09-29.

Raw files: [`bench/results/2026-09-29-m4.4-decode/`](../../bench/results/2026-09-29-m4.4-decode/).
Reproduce with `bench/run-m4.4-decode-profile.sh` (profile + lever screen) and
`bench/run-m4.4-turn-check.sh` (turn regression + needle), both under the shared
single-GPU flock ([BAS-80](/BAS/issues/BAS-80)).

## TL;DR

1. **The decode step is not MoE-matmul-bound.** The MoE expert matmul is **10.3%**
   of the decode-step GPU time. The largest GPU term is the **dense matmul set
   (40.3%)**, and the largest single op is the **flash attention over the KV
   (17.7%)**. The largest single *non-GPU* term is the host/scheduler path
   (**~20 ms of a 59 ms step, ~34%**). The M4.2 upload is not in the decode path
   at all: the M4.2 probe counts **zero** used-expert copies per decode graph.
2. **The `--n-cpu-moe` layers are computed on the CPU during decode.** Vulkan's
   `offload_op` requires a batch of at least `GGML_OP_OFFLOAD_MIN_BATCH` (default
   32) and `MUL_MAT_ID`'s batch is the token count, which is 1 in decode. So the
   16 host-resident expert FFNs run on the CPU (no upload, no GPU op).
   `GGML_OP_OFFLOAD_MIN_BATCH=1` moves them to the GPU and is **neutral**
   (16.7 vs 17.0 tok/s), so the CPU compute and the GPU copy+compute cost about
   the same.
3. **The lever that pays is placement.** `--n-cpu-moe 12` at the 128K engine
   context takes 4K decode from **17.0 to 19.6 tok/s (+15.5%)**, with the 16K and
   128K cached delta turns inside 1% and the needle passing. `--n-cpu-moe 10` and
   `8` **fail to load** at `--ctx 131072`, so **12 is the placement ceiling**.
4. **The 4K decode gate (`>=25 tok/s`) is not reachable from the host side.** One
   decode step is 51.0 ms at the best placement; the measured **GPU-busy floor is
   38.7 ms (25.8 tok/s)**, so the gate needs a ~25-30% *GPU* reduction, not a host
   one. See [Measured ceiling](#measured-ceiling-and-recommendation).

## Method

Two harnesses, one GPU hold each, one server restart per config.

**Profile.** `bench/run-m4.4-decode-profile.sh profile16` starts llama-server with
`GGML_VK_PERF_LOGGER=1` and `GGML_VK_PERF_LOGGER_FREQUENCY=1`, primes the
4096-token prefix with one request, then measures a second request with the same
prompt and `cache_prompt=true`. That request reuses 4090 cached tokens, so every
graph it computes is a one-token graph: a decode step at a 4096-token context.
`bench/analyze-decode-perf.py` selects the perf blocks after that request's
`launch_slot_` line and drops the suffix-prefill graph (the only graph in the
window whose flash-attention query has more than one token).

The llama.cpp scheduler splits one decode token into **~16 Vulkan sub-graphs**
(one per MoE/offload boundary), so a decode step is a run of perf blocks, not one
block; the table below is the per-step sum over the 16 decode graphs.

**Lever screen.** `bench/run-m4.4-decode-profile.sh` also runs the shipped decode
measurement per config: a 4096-token prompt and 128 generated tokens, three
repeats, `cache_prompt=false`, after a discarded warm-up. That is the same
workload as `bench/run-m4.2-decode4k.sh`, so the numbers are comparable with
M4.1/M4.2 (17.6 / 18.1 tok/s).

**Attribution probe.** The M4.2 engine carries `GGML_SCHED_UPLOAD_STATS=1`, which
prints, once per decode graph, the number of host-resident expert tensors, copy
calls, bytes copied and the main-thread time in the used-experts branch.

## Result 1 — the ranked cost of one 4K decode step

Raw: `profile16/llama-server.log`, `profile16/vk-perf-decode.json`,
`profile16/perf-run.json`. 16 decode graphs, 15.9 GPU sub-graphs per step,
**GPU busy 38.72 ms per decode step**.

| rank | GPU term | ms/step | % of GPU |
| --: | --- | --: | --: |
| 1 | **dense matmul (`MUL_MAT*` not `MUL_MAT_ID`)** | **15.587** | **40.3%** |
| 2 | **full attention (`FLASH_ATTN_EXT` over the KV)** | **7.948** | **20.5%** |
| 3 | norms / activations / softmax (`RMS_NORM`, `SILU`, `TOP_K`, …) | 4.790 | 12.4% |
| 4 | MoE expert matmul (`MUL_MAT_ID`) | 4.006 | 10.3% |
| 5 | memory-layout ops (`CONT`, `CPY`, `GET_ROWS`, `SET_ROWS`, …) | 2.297 | 5.9% |
| 6 | other | 2.202 | 5.7% |
| 7 | elementwise (`ADD`, `MUL`, `SCALE`, …) | 1.376 | 3.6% |
| 8 | GatedDeltaNet / SSM (`GATED_DELTA_NET`, `SSM_CONV`) | 0.514 | 1.3% |
| | **GPU busy total** | **38.721** | **100%** |

Largest individual ops, same window:

| ms/step | % of GPU | op |
| --: | --: | --- |
| 6.868 | 17.7% | `FLASH_ATTN_EXT q(256,1,24,1) k(256,4352,2,1)` — attention over the cached KV |
| 2.803 | 7.2% | `MUL_MAT_ID_VEC iq2_s m=640 n=10 k=2560 n_expert=512` |
| 2.004 | 5.2% | `MUL_MAT_VEC iq4_xs m=10240 n=1 k=2560` |
| 1.863 | 4.8% | `MUL_MAT_VEC bf16 m=320 n=1 k=10240` |
| 1.850 | 4.8% | `MUL_MAT_VEC bf16 m=10240 n=1 k=320` |
| 1.215 | 3.1% | `MUL_MAT_VEC iq4_xs m=2560 n=1 k=6144` |
| 1.101 | 2.8% | `TOPK_MOE_EARLY_SOFTMAX_NORM SOFT_MAX` |

**Named dominant terms.** On the GPU: the **dense matmul set (40.3%)**, with
flash attention over the KV as the single largest op (17.7%). On the host:
**~20 ms of the 59 ms step** is not GPU-busy.

### The wall-clock split

The non-perf decode run (`decode16`) is **59.0 ms/token = 16.96 tok/s**, so
38.7 ms is GPU-busy and **~20 ms (~34%) is host/scheduler/CPU**. The perf-logger
run itself is slower (14.3 tok/s) because `GGML_VK_PERF_LOGGER` forces a
`waitForFences` per sub-graph, so the wall number to use is the non-perf one.

### The host term is CPU expert compute, not an upload

`stats16/llama-server.log` (M4.2 probe, raw):

| graph | layers | copies | bytes | branch_ms |
| --- | --: | --: | --: | --: |
| prefill (warm-up, 8 tokens) | 48 | 5802 | 4.46 GB | 54.3 |
| **decode (each of 24 steps)** | **0** | **0** | **0** | **0.00** |

The used-expert upload that M4.2 fixed does **not** happen during decode: the 16
`--n-cpu-moe` layers' expert FFNs are executed on the CPU. The mechanism is in
the engine, not in the flags:

- `ggml_vk_get_op_batch_size(MUL_MAT_ID)` returns `op->ne[2]`, which is the
  **token count** of the MoE op (`ggml/src/ggml-vulkan/ggml-vulkan-debug.cpp`).
- `ggml_backend_vk_device_offload_op` offloads only when
  `batch >= op_offload_min_batch_size`, and that defaults to **32**
  (`GGML_OP_OFFLOAD_MIN_BATCH`, `ggml/src/ggml-vulkan/ggml-vulkan.cpp`).
- Decode is 1 token, so `1 >= 32` is false: the op stays on the CPU backend,
  where its host-resident weights already are.

This is why M4.1/M4.2 measured decode as flat to the upload fix: there is no
upload to fix at batch 1. It also refines the M4.1 host-split reading of "CPU
backend workers execute 0 ms" — for the *decode* case in the same probe the
seven CPU worker threads each accumulate **1240 ms per 32 tokens (38.8 ms/token)**
at 16K (`bench/results/2026-09-29-host-cpu/ctx16k/lm_none/profile-host-split.json`,
case `decode_p16384`), versus 80–100 ms for the prefill cases.

## Result 2 — the flag-gated lever screen (4K decode, 3 repeats)

Raw: one directory per config under
`bench/results/2026-09-29-m4.4-decode/`, each with `decode4k.json`,
`command.txt`, `env.txt` and `llama-server.log`.

| config (one variable vs the next) | 4K decode tok/s (3 runs) | median | vs baseline |
| --- | --- | --: | --: |
| `decode16` — shipped decode config, `--n-cpu-moe 16` | 16.93 / 16.96 / 17.81 | 16.96 | — |
| `decode_offload1` — `GGML_OP_OFFLOAD_MIN_BATCH=1` | 16.69 / 16.69 / 16.62 | 16.69 | −1.6% |
| `decode_t16` — `--threads 16 --threads-batch 16` | 6.02 / 5.63 / 6.27 | 6.02 | −64% |
| `decode_forcemmvq` — `GGML_VK_FORCE_MMVQ=1` | 16.45 / 17.52 / 17.76 | 17.52 | +3.3% |
| `decode_nc12` — `--n-cpu-moe 12` | 18.98 / 19.59 / 19.61 | **19.59** | **+15.5%** |
| `decode_offload1_nc12` — both | 17.87 / 17.89 / 17.89 | 17.89 | +5.5% |

Reading:

- **The lever is placement.** Moving 4 of the 16 CPU-resident expert layers to
  the GPU is worth **+15.5%**. Fewer CPU-resident layers are less work on the
  serial CPU path and more of the step overlaps on the GPU.
- **Offloading the batch-1 MoE ops is a wash** (−1.6% alone, +5.5% with
  placement, i.e. well behind placement alone). The GPU copy+compute path costs
  about what the CPU i-quant path costs at batch 1, which is exactly what the
  engine's 32-token offload threshold is calibrated for.
- **More CPU threads is a large regression** (−64%), reproducing M4.1's
  `threads16` decode result (11.3 → 5.4 tok/s). The CPU worker pool competes with
  the main host thread that drives the Vulkan sub-graphs.
- `GGML_VK_FORCE_MMVQ` is within noise (+3.3% on one config, and the decode16
  baseline itself spanned 16.93–17.81).

### Placement ceiling

Two further placement probes at `--ctx-size 131072`, same engine and levers, both
**fail to load** (raw `FAILED.json` + `llama-server.log` in the config directory):

| config | result |
| --- | --- |
| `decode_nc10` — `--n-cpu-moe 10` | load fails: `ggml_gallocr_reserve_n_impl: failed to allocate Vulkan1 buffer of size 1106059268` / `failed to allocate compute pp buffers` |
| `decode_nc8_128k` — `--n-cpu-moe 8` | load fails: `vk::Device::allocateMemory: ErrorOutOfDeviceMemory` / `failed to allocate buffer for kv cache` |

So `--n-cpu-moe 12` is the last value that fits at the 131072 context with this
engine configuration, and 4K decode 19.6 tok/s is the **placement ceiling**. The
old M2/ADR-0003 VRAM model capped the 128K expert budget at 22.4 GiB (n=16); with
`--load-mode none` and the M4.2 levers the box now runs 25.0 GiB of GPU-resident
experts, but not more.

Raw: `turns/nc12/profile-host-split.json`, `turns/nc12/harness.log`,
`turns/nc12/needle.json`, `turns/nc12/llama-server.log`.

The 128K leg also proves the placement is *safe*, not just fast: a 127 998-token
cold prefill completes at `--ctx-size 131072` with `--n-cpu-moe 12`, which is the
worst case for the VRAM budget at that context.

Reading: the placement lever is a **4K-specific** win. At 16K the moved layers are
free (the numbers are flat), because at 16K the GPU attention term is ~4x the 4K
term and the CPU-resident expert FFN is already hidden behind it. At 4K the GPU
tail is short enough that the CPU expert FFN is exposed, so taking 4 layers off
the CPU shortens the step by 8 ms.

## Measured ceiling and recommendation

The gate is **not reachable**, and the reason is arithmetic rather than an
unlucky lever:

- Best measured step (nc12): 51.0 ms = 19.59 tok/s. The target is 40.0 ms.
- GPU busy per step, measured on the nc16 profile: **38.7 ms**. The 4 extra
  GPU-resident layers add ~0.5 ms (the GPU MoE term is 0.125 ms/layer), so
  **nc12 GPU-busy is ~39 ms**, i.e. **25.5-25.8 tok/s with zero host time**.
- Host time at nc12 is therefore ~12 ms, and the gate needs it to be ~1 ms.

A `>=25 tok/s` target can only come from a **GPU-side** reduction, and the three
generic terms that would have to move are the dense matmul set (40.3%), flash
attention over the KV (20.5%; the single largest op at 17.7%) and the MoE expert
matmul (10.3%). The MoE term — the term M4.2 named as the decode bottleneck —
carries only 4.0 ms of the 51 ms step, so the Vulkan integer/MMVQ path M3.1
sketched **cannot reach the gate even if it were free**.

Recommendation to the CTO: land `--placement auto` as the flag-gated lever (it is
in `bongo.sh`; default stays `tier` so nothing changes silently), keep
`--n-cpu-moe 12` at `--ctx 131072` as the measured best, and take a decode target
re-baseline to the CEO in the 20-24 tok/s range — or fund a GPU-side decode
milestone aimed at the attention + dense-matmul set, which is ~60% of the GPU
step and where the measured headroom actually is.

## Lever landing

`bongo.sh` gains `--placement tier|auto` (default `tier`):

- `tier` — the existing fixed per-tier split (`TIER_N_CPU_MOE`), unchanged.
- `auto` — `TIER_N_CPU_MOE_SMALL_CTX` when `--ctx 131072` or less, `TIER_N_CPU_MOE`
  above it. For `iq2_xs` that is 12 instead of 16 at the shipped default context
  (131072) and 16 at 256K, so the 256K path cannot regress into an out-of-VRAM
  placement. Tiers with no measurement fall back to the per-tier value.
- An explicit `--n-cpu-moe N` overrides both.

Covered by `tests/bongo-sh.test.sh` (six new M4.4 cases: tier default, auto at
131072, auto falling back above 131072, explicit override, unmeasured-tier
fallback, and rejection of an unknown mode). Because `--n-cpu-moe 12` is the
*load ceiling* at this context (10 and 8 OOM), `tier` remains the default and the
CTO decides whether to flip it.

## What was not tried

- **A Vulkan integer/dot-product path for the i-quant expert matmul** (the
  Vulkan analogue of the M3.1 SYCL patch). The profile says the term is 4.0 ms of
  a 51 ms step, so even a free expert kernel cannot reach the gate; the work is
  not worth funding for this target.
- **Kernel-level attention work** (`FLASH_ATTN_EXT` over the KV is the largest
  single op at 6.9 ms/step). This is where the measured headroom is, but it needs
  a warptile/heuristic change in the Vulkan FA path, which is a milestone of its
  own rather than a config lever.
- **`--cache-type-v f16`** and other KV-precision changes: they move numerical
  behaviour and the 256K memory budget, and the KV term is not the largest.
