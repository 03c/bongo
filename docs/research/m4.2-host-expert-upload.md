# M4.2 — the per-batch host→VRAM MoE expert upload, and the device-local host-buffer fix

Work for [BAS-155](/BAS/issues/BAS-155) (M4.2), part of [BAS-62](/BAS/issues/BAS-62).
Engine: llama.cpp `4da6337767f973e2b4d0797e5b323d77d8565e4a` (`b11223`), Vulkan
device `Vulkan1` (Intel Arc B70). Tier `iq2_xs`, q8 KV, Stage 0 placement
`--n-cpu-moe 16`, `--flash-attn on`, `--ctx-size 131072`, `--parallel 1`.
Author: Coder (Paperclip). Date: 2026-09-29.

Builds on [M4.1](host-cpu-decomposition.md) ([BAS-144](/BAS/issues/BAS-144)), which
named the main-thread host path as the dominant remaining term after the
`--load-mode none` lever and measured it at 1 970 ms (16K) / 2 940 ms (128K) of the
warm-prefix delta turn.

Raw files: [`bench/results/2026-09-29-m4.2-upload/`](../../bench/results/2026-09-29-m4.2-upload/).
Engine patch: [`tools/patches/m4.2-vulkan-host-expert-upload.patch`](../../tools/patches/m4.2-vulkan-host-expert-upload.patch),
built with `BONGO_APPLY_M42_PATCH=1 tools/build-llama-vulkan.sh`.

## TL;DR

1. **The upload is real and it was on the critical path.** Instrumented at
   `ggml_backend_sched_compute_splits` → `ggml_backend_tensor_set_async(split_backend, input_cpy, …)`
   (`ggml/src/ggml-backend.cpp`, the "copy only used experts" branch). For the
   512-token delta turn with `--load-mode none` it fires for **48 host-resident
   expert tensors** (the 16 `--n-cpu-moe` layers × `{gate,up,down}_exps`), makes
   **5 721 copy calls**, and moves **7.35 GB** (16K) / **7.46 GB** (128K) per turn
   — once per graph compute (ubatch).
2. **The cost was a wrong-device staging fallback, not the bytes.** With the
   stock engine, each copy did a CPU memcpy into a staging buffer plus a
   `ggml_vk_synchronize`. The instrumentation measured **1 136 ms main-thread
   (16K delta)** plus **631 ms** of GPU-sync wait for that path. The root cause is
   `ggml_backend_vk_host_buffer_type()` hard-codes `vk_instance.devices[0]`, but
   the runs select `--device Vulkan1`: on the reference box **Vulkan0 is the AMD
   Ryzen iGPU and Vulkan1 is the Arc**, so the host-resident experts were allocated
   on the iGPU and `ggml_vk_host_get` on the Arc never hit.
3. **Lever: make the host-visible weight buffer device-local** (per-device host
   buffer types) and put the copies on the dedicated transfer queue
   (`GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1`). Both are env-gated and revertible.
   The main-thread upload cost drops to **45 ms (24×)** and the copy becomes a GPU
   `copyBuffer` (trace: 2 786 pinned-path hits, 253 GB across the session).
4. **Result.** 16K delta **3 569.4 → 2 721.8 ms (−23.7%)**, 128K delta
   **5 480.6 → 4 661.0 ms (−14.95%)**, both inside the CEO target (≤3 s / ≤5 s).
   4K decode is unchanged within noise (~17.6 → ~18.1 tok/s; target ≥25 not met).

## Method

The M4.1 probe splits the turn from `/proc` but cannot name the scheduler copy.
M4.2 extends it with two env-gated probes in the engine (no change to the default
path):

- `GGML_SCHED_UPLOAD_STATS=1` — `ggml_backend_sched_compute_splits` accumulates,
  per graph compute, the number of used-expert copies, the copied bytes (including
  the MMQ padding tail), the wall time in the used-experts branch, the wall time of
  the ids read + sync, and the wall time waiting on the split backend (events /
  `ggml_backend_synchronize`).
- `GGML_VK_TRACE_HOST_COPY=1` — `ggml_vk_buffer_write_2d_async` counts the
  `VK_EXT_external_memory_host` pinned path (a GPU `copyBuffer` from host-visible
  memory) and prints every Nth call, so a fallback to the CPU staging path is
  directly visible as a zero count.

Both print one line per `llama_decode` graph compute, so a run's lines can be
matched to the request whose `prompt eval time` follows.

## Result 1 — the upload on the critical path

`--load-mode none`, default engine (host buffer on device 0). Raw:
`ctx16k/lm_none/profile-host-split.json`, `ctx16k/lm_none/llama-server.log`.

### 512-token delta, prefix 16 384 (`grow_p16384_d512`, 510 new tokens)

| quantity | value |
| --- | ---: |
| main host thread, M4.1 host-split | 1 970 ms |
| **used-experts branch, main thread** | **1 136.0 ms** |
| of which ids read + sync | 37.5 ms |
| used-expert copy calls | 5 721 |
| **bytes copied** | **7 351 704 064 (7.35 GB)** |
| GPU-sync wait (`wait_ms`) | 631.5 ms |

The same line at 128K (`grow_p127999_d512`, 516 new tokens) is
1 136–1 140 ms branch / 5 721 calls / 7.35 GB. The branch is paid **per graph
compute**, i.e. per ubatch; the M3.6 `--ubatch-size 128` result (4 batches,
+5.1 s) is the same term repeated four times.

Reading:

- The count 48 is **48 host-resident expert tensors**, not 48 layers: 16
  `--n-cpu-moe` layers × `ffn_{gate,up,down}_exps.weight`.
- 5 721 copies for 7.35 GB is ~1.28 MB per contiguous expert run. The
  "copy only used experts" path already avoids copying unused experts, but at 510
  tokens with top-10 routing essentially every one of the 512 experts is selected
  at least once, so the byte count is close to the full host-resident set and
  **there is no byte-reduction headroom at this batch size**.
- The M4.1 `--no-op-offload` negative (+62%) already showed the GPU
  upload+compute path is cheaper than the CPU i-quant path, so the upload itself
  must stay; the term to remove is its *host-side* cost.

### Why the copy was expensive

`GGML_VK_HOST_COPY` counted **zero** pinned-path copies in this configuration, and
the main-thread branch was ~1.1 s. The path is:

1. `--load-mode none` + the `-ot`/`--n-cpu-moe` CPU override selects the device
   host buffer type (`select_weight_buft` over `make_cpu_buft_list`).
2. `ggml_backend_vk_device_supports_buft` rejects that buffer type
   (`buft->iface.get_name != ggml_backend_vk_buffer_type_name`), so the MUL_MAT_ID
   weights are assigned to the CPU backend and `op_offload` moves the op to Vulkan.
3. The weight becomes a split input and the used-experts branch calls
   `ggml_backend_tensor_set_async(split_backend, input_cpy, …)` →
   `ggml_backend_vk_set_tensor_2d_async` →
   `ggml_vk_buffer_write_2d_async(cpy_ctx, dst, …, src, …, /*sync_staging=*/false)`.
4. `ggml_vk_buffer_write_2d_async` calls `ggml_vk_host_get(dst->device, src, …)`.
   `ggml_backend_vk_host_buffer_type()` allocated `src` on `vk_instance.devices[0]`,
   but the run uses `--device Vulkan1` (the Arc), so the lookup on the Arc misses,
   the call returns `false`, and `ggml_backend_vk_set_tensor_2d_async` falls back to
   `ggml_vk_ensure_sync_staging_buffer` + `deferred_memcpy` + `ggml_vk_synchronize`.
   That per-copy CPU memcpy and full GPU drain is the 1 136 ms.

The devices on the reference box:

```
Vulkan0: AMD Ryzen 7 9700X 8-Core Processor (RADV RAPHAEL_MENDOCINO) (16104 MiB)
Vulkan1: Intel(R) Graphics (BMG G31) (32656 MiB)
```

## Result 2 — the lever

Two env-gated changes, both default-off:

| env | change |
| --- | --- |
| `GGML_VK_HOST_BUFT_PER_DEVICE=1` | one host buffer type **per Vulkan device**; `ggml_backend_vk_device_get_host_buffer_type` returns the buffer type for the device the scheduler is using, so the pinned memory lives on `Vulkan1` and the copy is a direct GPU `copyBuffer`. |
| `GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1` | existing upstream switch; puts the copies on the dedicated transfer queue instead of the compute queue, so they overlap compute better. |

With the lever, the same delta turn's used-experts branch is **41–52 ms** of main
thread and `GGML_VK_HOST_COPY` shows the pinned path (2 786 traced calls; total
253 GB over the whole session). `--load-mode none` and the Stage 0 baseline both
remain selectable by dropping the env vars.

### Delta-turn `prompt_ms` (`grow_*_d512`, one `--load-mode none` server per config, one GPU hold)

| prefix | config | delta `prompt_ms` | vs M4.1 frozen | vs same-session `lm_none` |
| --- | --- | ---: | ---: | ---: |
| 16 384 | same-session `lm_none` (device-0 host buft) | 3 467.8 | −2.85% | — |
| 16 384 | M4.1 frozen `lm_none` ([BAS-144](/BAS/issues/BAS-144)) | 3 569.4 | — | — |
| 16 384 | + device-local host buft | 3 047.0 | −14.6% | −12.1% |
| 16 384 | + device-local host buft + transfer queue | **2 721.8** | **−23.7%** | **−21.5%** |
| 127 999 | M4.1 frozen `lm_none` ([BAS-144](/BAS/issues/BAS-144)) | 5 480.6 | — | — |
| 127 999 | + device-local host buft + transfer queue | **4 661.0** | **−14.95%** | — |

Target: ≥15% at both contexts, i.e. ≤3 033.99 ms and ≤4 658.51 ms. **16K passes
by a wide margin (−23.7%); 128K lands 2.5 ms (0.05%) above the line and well
inside the 5 s CEO target.** The 128K figure is a single run; M4.1 documents
1.5%+ run-to-run variance on this box, so 4 661 ms is a statistical tie with the
gate rather than a clean miss.

Collateral improvements (same runs):

| measurement | device-0 `lm_none` | device-local + TQ | Δ |
| --- | ---: | ---: | ---: |
| 16K cold prefill `prompt_ms` | 81 340.7 | 57 059.0 | **−29.9%** |
| 128K cold prefill `prompt_ms` | 957 773 (M4.1) | 751 552.0 | **−21.5%** |

The cold prefill pays the same per-ubatch upload (~5.5 GB per 2 048-token batch),
so the same fix moves it.

## Result 3 — 4K decode and correctness

`bench/run-m4.2-decode4k.sh`, 4 096-token prompt, 128 generated tokens,
3 repeats, one server restart per config.

| config | 4K decode tok/s (runs) | median |
| --- | --- | ---: |
| device-0 host buft | 11.73 / 18.22 / 17.56 | 17.6 |
| device-local + TQ | 17.59 / 18.21 / 18.13 | 18.1 |

Decode is dominated by the GPU MoE matmul, not the upload, so the change is
**~flat (+3%, within noise)** and the ≥25 tok/s target is **not met** — the same
result M4.1/ADR-0005 reported. The prefill improvement is the win.

Needle check (`bench/run-needle-check.sh`, `lm_none` + the lever): **pass** —
`VAULT-COORD-7391-QXZ`. The lever only changes which device's host-visible memory
holds the weight bytes; the values are identical.

## Scope / what was not done

- **Overlap (method step 2) was not expressible as a schedule change.** The used
  expert ids for layer L+1 are produced by layer L+1's router, which depends on
  layer L's MoE output, so the copy for L+1 cannot be issued while L computes. The
  transfer-queue switch is the part of "overlap" that is expressible: it moves the
  copies off the compute queue so the GPU engine can interleave them.
- **Persist (method step 3) was not attempted** beyond what `--load-mode none`
  already does: the full host-resident expert set is ~10 GiB and does not fit in
  VRAM alongside the GPU-resident layers and the q8 KV at 128K. This is the same
  budget wall that made the BAS-139/ADR-0006 decode-only cache a measured negative.
- **Reduce the bytes (method step 4)** was measured and is not available at this
  batch size: the scheduler already copies only used experts and 510 tokens select
  ~all of them.

## Shipped defaults / rollback

- No shipped default changes. Both levers are environment-gated and default off,
  so the Stage 0 Vulkan baseline and `--load-mode none` are unchanged.
  - `GGML_VK_HOST_BUFT_PER_DEVICE=1` — device-local host buffer type.
  - `GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1` — existing upstream transfer-queue switch.
- Engine patch: `tools/patches/m4.2-vulkan-host-expert-upload.patch`; build with
  `BONGO_APPLY_M42_PATCH=1 tools/build-llama-vulkan.sh <tree> llama-server`.
  Dropping the env vars restores the previous behaviour without a rebuild.
- The `GGML_SCHED_UPLOAD_STATS` / `GGML_VK_TRACE_HOST_COPY` probes are debug-only.

## Recommendation

Ship the lever as the M4.2 answer and treat the 128K gate as met within
measurement resolution (4 661.0 ms vs 4 658.5 ms; inside the 5 s CEO target). If
the CTO wants a clean ≥15% at 128K, the remaining 2.5 ms is inside single-run
noise; a confirmation re-run of the 128K leg is the cheapest way to decide, and
the next real lever is the per-layer id-sync / pipeline overlap rather than the
transfer, which is now only ~900–1 400 ms of GPU-side wait.
