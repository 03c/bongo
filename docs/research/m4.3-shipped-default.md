# M4.3 — the M4.2 upload fix shipped as the `bongo.sh` default

Work for [BAS-158](/BAS/issues/BAS-158) (M4.3), part of [BAS-62](/BAS/issues/BAS-62).
Builds on [M4.1](host-cpu-decomposition.md) ([BAS-144](/BAS/issues/BAS-144)) and
[M4.2](m4.2-host-expert-upload.md) ([BAS-155](/BAS/issues/BAS-155)).
Author: Coder (Paperclip). Date: 2026-09-29.

M4.2 met the turn targets, but only with two environment-gated, default-off
levers. This milestone makes that configuration the shipped default and confirms
the targets on it.

## What shipped

`./bongo.sh` now, by default:

1. **Selects the M4.2-patched Vulkan engine.** The pinned tree is cached at
   `$BONGO_HOME/engine/llama.cpp-pin` (`$BONGO_ENGINE_DIR`). When it is missing
   and docker + the Vulkan build image are available, bongo.sh clones
   llama.cpp at the pinned commit and builds it with
   `BONGO_APPLY_M42_PATCH=1 tools/build-llama-vulkan.sh`. `--llama-bin DIR` still
   overrides the selection; an unpatched build automatically turns the levers
   off instead of pretending they work.
2. **Passes `--load-mode none`** (the M4.1 lever) unless the user sets
   `--load-mode`.
3. **Sets `GGML_VK_HOST_BUFT_PER_DEVICE=1` and
   `GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1`** on the `llama-server` process. The user
   does not need to know them.

The opt-out is `--engine stage0` (or `BONGO_ENGINE=stage0`): it uses the stock
prebuilt, omits `--load-mode`, and drops both env vars — the Stage 0 Vulkan
`--ctx 131072 --n-cpu-moe 16` baseline — **without a rebuild**, because the M4.2
patch is env-gated. `--no-m42-upload` is the finer-grained switch: keep the
patched engine, turn only the levers off. Both are documented in
[`docs/bongo-sh.md`](../bongo-sh.md).

## Result — the shipped default reproduces M4.2

Raw: [`bench/results/2026-09-29-m4.3-shipped-default/`](../../bench/results/2026-09-29-m4.3-shipped-default/).
Engine: llama.cpp `4da6337767f973e2b4d0797e5b323d77d8565e4a` (`b11223`) + the M4.2
patch, Vulkan `Vulkan1` (Intel Arc B70), tier `iq2_xs`, q8 KV, `--n-cpu-moe 16`,
`--load-mode none` + both env vars, 512-token delta turn, one server restart per
config, one GPU-lock hold (BAS-80).

| leg | M4.2 | M4.3 shipped default | Δ vs M4.2 | vs M4.1 frozen | target |
| --- | ---: | ---: | ---: | ---: | --- |
| 16K delta `prompt_ms` | 2 721.8 | **2 716.1** | −0.2% | −23.9% | ≤3 000 ✓ |
| 128K delta `prompt_ms` | 4 661.0 | **4 669.3** | +0.18% | **−14.80%** | ≤5 000 ✓ |
| 16K cold prefill `prompt_ms` | 57 059.0 | 57 038.5 | −0.04% | — | no >2% regression ✓ |
| 128K cold prefill `prompt_ms` | 751 552.0 | 751 959.7 | +0.05% | — | no >2% regression ✓ |

Both legs sit inside the CEO target and reproduce M4.2 within run-to-run noise
(the box shows ≥1.5% variance). The 128K re-run lands at **4 669 ms / −14.80% vs
the M4.1 frozen baseline**, i.e. the 14.95% of M4.2 and this run are the same
number inside noise: the 128K figure is a **statistical tie with the 15% gate**,
and the meaningful gate — `≤5 s` — is met with **331 ms of margin**.

Needle check on the shipped default: **pass** — `VAULT-COORD-7391-QXZ`
(`needle/shipped_default/needle.json`). The lever only changes which device's
host-visible memory holds the weight bytes, so the values are identical.

## The Stage 0 opt-out is the slow path (the A/B)

`stage0_optout` in the same session is the exact `bongo.sh --engine stage0`
configuration on the same engine binary (env unset, no `--load-mode`):

| 16K delta turn | shipped default | `--engine stage0` |
| --- | ---: | ---: |
| delta `prompt_ms` | **2 716.1** | 5 637.6 |
| in-turn disk read (delta) | 1.7 MB | **566 MB** |
| server VmRSS after the turn | 2.45 GiB | **10.6 GiB** |

The 566 MB read is the in-turn `mmap` re-read of the host-resident expert set —
the cost `--load-mode none` removes. The opt-out runs it, so the default is the
fast path and the opt-out is a real, measured regression to the Stage 0
behaviour (its absolute number is page-cache-dependent; the historical M3.6
16K delta was ~3.98 s with a warm page cache).

## RAM footprint on the 30 GiB box

The brief expected `--load-mode none` to hold a ~10 GiB host-resident set in
anonymous RAM. The measurement corrects that in a useful direction:

- With the shipped default (`--load-mode none` + the device-local host buffer),
  the server's **VmRSS is 2.3–2.5 GiB** at 16K and 128K. The host-resident
  expert set is in the device-local **pinned host buffer**, not charged to the
  process's anonymous RSS.
- The ~10 GiB figure is the **Stage 0 `mmap` working set**: the same config
  without `--load-mode none` reports **VmRSS 9.5–10.6 GiB** and re-reads 566 MB
  in the turn.
- System-wide during the 128K default run: **MemAvailable stayed ≈10 GiB**,
  `SwapFree` did not move (20.7 of 23 GiB), and there were no OOM events.
- The 256K default (`--ctx 262144 --n-cpu-moe 18`) with the levers:
  `ctx256/ctx256-fit.json` — healthy after **75 s**, one tiny request returns
  **200**, **VRAM peak 30.65 GiB** (≈1.2 GiB below the 31.85 GiB device-loss
  point), **MemAvailable 10.3 GiB**.

**Verdict: safe on the 30 GiB box.** The shipped default is *cheaper* in
anonymous RAM than the Stage 0 baseline, not more expensive. The safe
combination is the shipped one; no change needed.

## Reproduce

```sh
# tests (no GPU)
bash tests/bongo-sh.test.sh

# the shipped default's flags / env / engine, no GPU work
./bongo.sh --dry-run --runtime dir --runtime-dir "$HOME/.bongo/runtime"

# the measured session (one GPU-lock hold)
bench/run-m4.3-shipped-default.sh

# or just the shipped-default legs against an existing patched engine
BONGO_HOST_SPLIT=1 \
  BONGO_LLAMA_SERVER="$HOME/.bongo/engine/llama.cpp-pin/build-vulkan/bin/llama-server" \
  BONGO_PROFILE_OUT=bench/results/2026-09-29-m4.3-shipped-default/turns \
  BONGO_PROFILE_CONFIGS=shipped_default,shipped_default_128k,stage0_optout \
  BONGO_PROFILE_DELTAS=512 bench/run-warm-prefix-profile.sh
```

The harness configs `shipped_default`, `shipped_default_128k` and
`stage0_optout` mirror bongo.sh's default and opt-out exactly.

## Scope / what was not done

- **Decode `≥25 tok/s` is still open** (~18 tok/s, M4.2/M4.4). It is a separate,
  GPU-MoE-matmul-bound axis; M4.3 changes none of it.
- A full 256K cached delta turn was not timed (a 256K cold prime is ~30+ min);
  the fit/load/one-request spot check is the M4.3 acceptance for that leg.
