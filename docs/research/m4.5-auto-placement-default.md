# M4.5 — `--placement auto` is the default, with a load fallback

Work for [BAS-163](/BAS/issues/BAS-163) (M4.5), part of [BAS-62](/BAS/issues/BAS-62).
Engine: llama.cpp `4da6337767f973e2b4d0797e5b323d77d8565e4a` (`b11223`) plus the
M4.2 patch (`tools/patches/m4.2-vulkan-host-expert-upload.patch`).
Backend Vulkan device `Vulkan1` (Intel Arc Pro B70), tier `iq2_xs`, q8 KV,
`--flash-attn on`, `--load-mode none`, M4.2 upload levers on
(`GGML_VK_HOST_BUFT_PER_DEVICE=1 GGML_VK_ASYNC_USE_TRANSFER_QUEUE=1`).
Author: Coder (Paperclip). Date: 2026-09-29.

Raw files: [`bench/results/2026-09-29-m4.5-auto-default/`](../../bench/results/2026-09-29-m4.5-auto-default/).
Reproduce with `bench/run-m4.5-default.sh` under the shared single-GPU flock
([BAS-80](/BAS/issues/BAS-80)); it drives `./bongo.sh` itself, not llama-server
directly, so the config and the plan output are the ones a user gets.

## TL;DR

1. **The default is now `--placement auto`.** At `--ctx 131072` it resolves to
   `--n-cpu-moe 12` (the M4.4 decode lever) and the shipped default measures
   **19.56 tok/s** 4K decode, matching the M4.4 lever screen (median 19.59) and
   **+15.3%** over the tier split (16.96).
2. **The auto placement is guarded.** If the server exits or fails the
   `/v1/models` health check, `bongo.sh` retries once at the safe split for the
   context and keeps serving. A forced OOM at `--n-cpu-moe 12` fell back to 16,
   recorded the fallback, preserved the failed log, and served (HTTP 200).
3. **The literal "16 above 131072" in the ticket is not loadable.** At
   `--ctx 262144` the reference box **device-lost** with `--n-cpu-moe 16`
   (`vk::DeviceLostError` / `ErrorDeviceLost`). The measured large-context safe
   split is **18** (30.39 GiB peak, ~1.5 GiB margin), so `auto` selects 18 above
   131072. This is the one deliberate deviation from the ticket text; see
   [The 262144 correction](#the-262144-correction). `--placement tier` still
   pins the fixed per-tier split (16).
4. **No turn or needle regression.** 16K cached delta turn 2721.2 ms (+0.19% vs
   the M4.3 shipped default), 128K 4745.7 ms (+1.64%), needle pass.
5. `bash tests/bongo-sh.test.sh` passes (70 cases), including the new default,
   the opt-out, and the forced-OOM fallback.

## Result 1 — the shipped default at 131072

`./bongo.sh --ctx 131072` (default flags) writes this into `bongo-config.json`:

```json
"placement": {
  "n_gpu_layers": 99,
  "policy": "auto",
  "auto_fallback": false,
  "auto_fallback_reason": null,
  "n_cpu_moe_requested": 12,
  "n_cpu_moe": 12,
  "load_mode": "none"
}
```

| measurement | value | gate |
| --- | ---: | --- |
| load + `/v1/models` + a request | ready, HTTP 200 | load + request — **pass** |
| VRAM peak | 31.415 GiB | below the 31.85 GiB device-loss point |
| RSS peak | 2.316 GiB | — |
| 4K decode (128 tokens, 3 runs) | **19.03 / 19.57 / 19.56 tok/s** | ~19.6 — **pass** |

The 4K decode median 19.56 tok/s is the M4.4 `decode_nc12` number (median 19.59)
reproduced through the shipped `bongo.sh` default, i.e. **16.96 -> 19.56 tok/s
(+15.3%)** versus the tier split (`decode16`, median 16.96).

## Result 2 — the forced-OOM fallback serves

`bench/run-m4.5-default.sh fallback` points `--llama-bin` at a wrapper engine
that exits with `vk::Device::allocateMemory: ErrorOutOfDeviceMemory` whenever it
sees `--n-cpu-moe 12`, and execs the real engine otherwise (the sibling
`libggml-vulkan.so` symlinks keep the M4.2-patched check green). `bongo.sh` is
run at `--ctx 131072`, so the auto placement requests 12.

| event | observation |
| --- | --- |
| attempt 1 (`--n-cpu-moe 12`) | exits 1 with the OOM line |
| preserved log | `$RUN_DIR/llama-server-auto-12.log` has the OOM line |
| retry (`--n-cpu-moe 16`) | ready, HTTP 200, VRAM peak 28.79 GiB |
| config | `auto_fallback: true`, `auto_fallback_reason: "out_of_device_memory"`, `n_cpu_moe_requested: 12`, `n_cpu_moe: 16` |
| plan output | `--n-cpu-moe 16 (auto -> tier (auto load fallback: out_of_device_memory))` |

The fallback triggers on **any** load failure (not only a recognised OOM
string), so an unknown driver OOM message on a different box is still guarded;
the reason field is only the classification. An explicit `--n-cpu-moe` disables
the fallback, and `--placement tier` never lowers the split, so neither is
overridden.

## Result 4 — the 262144 correction

The ticket's acceptance criteria say the default uses `--n-cpu-moe 16` above
131072. Run as written, the reference box **fails to load**:

```
terminate called after throwing an instance of 'vk::DeviceLostError'
  what():  vk::Queue::submit: ErrorDeviceLost
```

`--ctx 262144 --n-cpu-moe 16` is the value the 2026-09-28 fit already flagged
as unsafe (31.79-31.82 GiB against the 31.85 GiB device-loss point), and the
fallback to 16 would be a no-op because 16 *is* the requested value. The CTO's
decision was explicit: "do not ship a load-edge default that can fail on a
slightly different box or driver".

So `--placement auto` above 131072 resolves to the measured large-context safe
split, **18** for `iq2_xs`, and the fallback target is the same context-aware
safe value. The shipped default then serves:

| measurement | value |
| --- | ---: |
| `placement` | `policy: auto`, `n_cpu_moe_requested: 18`, `n_cpu_moe: 18`, `auto_fallback: false` |
| load + request | ready, HTTP 200 |
| VRAM peak | **30.393 GiB** (~1.5 GiB margin) |
| RSS peak | 2.044 GiB |

`--placement tier` and an explicit `--n-cpu-moe 16` still select 16 (the fixed
per-tier split); the docs mark that as unsafe at 262144. This deviation from the
ticket text is flagged on the issue for the CTO.
